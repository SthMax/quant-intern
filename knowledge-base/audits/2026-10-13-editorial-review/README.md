# 10月13日讲稿编辑审查

审查基线：`133c798`。审查日期：2026年10月13日。本文记录独立编辑意见，未修改研究正文、原始来源或计算数据。行号均对应该提交。

## 一、主要判断

五份材料已有充分研究内容。影响分享的主要问题是：**讲述顺序沿着核查工作展开，读者需要自己把核查记录还原成原理。** 一段常常先给结论，再列配置、版本和统计口径，最后补一串尚待验证事项。连续读几段以后，听众记住的是研究尚缺哪些证据，记不住机器如何工作。

此次改稿最有价值的变化是把主文改成连续讲解：先说要解决什么问题，再解释机器里发生了什么，用一两个数字说明影响，最后落到方案选择。公式、源码位置和详细来源保留在研究笔记与讲稿附注。

可以沿用第3周报告的写法。例如[应用章](../../../reports/phase2-technical-research-2026-09-18/applications.tex)先给出“两期财报和一份CSV”的任务，然后逐步说明模型、工具和产物。相比之下，本周读书稿经常在介绍机制之前先告诉读者“本轮核对的材料”“执行身份”“采用范围”。这类栏目适合研究台账。

此前[逐段修订记录](../../../reports/phase1-llm-industry-2026-09-09/editorial/assertive-revision.md)已经明确：正文介绍已有应用、解释作用，具体实验和实现条件集中到附录。本轮可以直接执行这条已经得到用户认可的编辑原则。

### 3. A100：三部分讲清楚“它为什么快，为什么放得下”

**第一部分：项目介绍与整体架构。** 四张A100、CPU内存、每层owner、专家分片、GPU内历史缓存画在一张图上。交代模型数据放在哪里，输入怎样进入，输出怎样返回。

**第二部分：inference speed提升。** 按“原来花什么时间→优化怎样减少它→哪类请求受益”讲：

- 低位存储与按块反量化：减少权重从显存搬入计算单元的数据量。
- CUDA Graph、设备侧同步和P2P：减少每层往返CPU以及多卡小消息的启动开销。
- 合批与专家复用：多个请求共享加载和计算机会，提高总吞吐。
- CED：长输入跳过大量decoder层的完整序列计算，主要改善prefill。
- 前缀完整状态：后续轮次保留历史计算，主要改善热续跑。
- MTP：一次主模型验证保留多个token，减少生成步骤。
- Jev：改成字段候选评分，改变了任务；模拟速度独立标识。

这一节需要明确基线。与“全量BF16常驻、逐层CPU启动、逐请求生成、每轮重算全文”等朴素路径相比，省了什么可以按源码解释；与成熟vLLM／SGLang相比是否更快，需要同任务对比数据。后一点集中说一次即可。现有资料适合说明优化来源和作用，尚不足以把每项技巧分别填成测得的倍数。不要将各节的不同速度倍数相乘。

**第三部分：显存优化。** 用四块账解释：压缩权重；Engram移到CPU；KV采用跨层共享和压缩结构；prefill通过分块和逐头处理缩小临时张量。将“模型本身已经有的压缩”与“项目具体存储／调度实现”标清楚。最后给一人和二十人长历史的显存增长，说明当前镜像缓存如何影响扩容。

### 4. AI Infra Book：用系统方法解释前面两个方案

这一节从前面留下的问题出发，用三段归纳：

- **时间花在哪里。** 计算、搬数据、通信和排队；用长历史下的权重＋KV读取解释合批收益变化。
- **多轮工作如何连续。** 缓存命中、工具等待、换出与恢复；用同一个Agent任务时间线说明。
- **预算怎样对准交付。** 模型GPU、工具CPU、驻留内存各有成本；以完成且合格的任务作为最终分母。
