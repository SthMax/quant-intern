# 两份独立逐页稿的共同约束

这是制作任务说明，不是 initial draft，也不是 PPT 内容。以同目录 initial-draft.md 和用户本轮直接要求为叙事依据。

用户本轮原话：

> 我觉得你这个转折比较好，重点应该是在可控的环境下使用，而不是硬讲安全风险。
>
> 先把我们对话的成果记录下来，这是我们最初步的initial draft，这个initial draft可以很松散，就像我们聊天这样，非常自然流畅，带有nuance，不要结构化。
>
> 第一个根据我们对话的成果，去知识库里面寻找对应的内容，并生成一个扩展之后的extended draft。第二个去阅读之前session的成果，特别是之前session里的report和git releases，然后生成另一个extended draft。
>
> 对于扩展之后的draft的要求：应该还是markdown格式，但是明确的包含ppt每一页的准确内容(也就是最终ppt在去除所有板式之后的样子，如果有图表，那么也在markdown中表示出来)，ppt大概30到35页，预计讲40分钟左右。
>
> 为了避免context污染，你只需要和subagent沟通就行，不要直接阅读它们的extended draft。

## 输出要求

- 交付 Markdown，30–35 页，预计约 40 分钟。这个页数包含封面和结尾；没有必要为了凑数做章节分隔页。当前不生成 PPTX、PDF 或网站。
- 每页有明确页码和最终标题，其下为会出现在 PPT 上的完整、准确文字。不能用“此处讲”“建议放”“展示一张图”等代替内容，也不能只交目录或概念说明。
- 必要的图表以 Markdown 表格、文本图或 Mermaid 完整表达，写清标签、单位、数据及关系。不要为了图表而制造不存在的数据。
- 逐页稿只含预定上屏内容。另建配套 evidence 文件放逐页来源、必要证据边界、时间分配和衔接说明，以免创作说明混入正式页面。若某个限定直接影响读者理解，仍需简洁地放在相应页面。
- 不默认每页都用同一套三点列举。不以统一模板牺牲语言和论证。既避免空泛口号，也避免把正文写成技术评审。
- 资料不足时选择有证据的表达或案例，不编造公司已部署、已验证收益、业务质量结果。明确区分研究、演示、估算、外部案例和实际实测，但不在正文反复堆叠免责声明。
- 旧稿的模型、硬件选择和技术结论需要检查时间、来源和适用条件。旧助手建议与用户认可分开。性能目标不能写成实测，吞吐测试不能写成质量评估，朋友的设备测试不能写成公司部署。
- 具体采用什么模型或方案，由相关证据与主线决定，不把已有材料目录直接搬成新稿。后半段结构尚未由用户定稿，两份稿允许独立探索。
- 公司与实习单位名称匿名处理；外部公开案例可保留原机构名称。以本地已有材料为首要来源，需核实易变数字或缺失关键事实时可访问权威原始来源，并记录。

## 协作边界

两位作者独立工作，不读对方 extended draft。知识库作者优先研究 knowledge-base，不读旧 session 和旧 final PPT 以免旧结构污染；旧成果作者明确阅读指定 session、report 和 git/GitHub releases，但不能把旧稿的组织方式视为定论。

两位作者只向主 agent 汇报文件路径、页数、预计时长、材料覆盖情况、未解决问题及完成状态。不要把 extended draft 全文、逐页目录或长篇摘录发给主 agent。主 agent 不直接读取两份 extended draft。

审稿 agent 可以完整阅读 initial draft、两份 extended draft 及 evidence 文件，独立检查主线、衔接、nuance、事实及40分钟容量。向主 agent 提交审查结论，可用少量页码和短摘录说明问题，不回传全文或完整目录。不擅自融合或重写两份稿。

除当前新建 narrative-drafts-2026-10-22 目录下自己的交付文件外，所有研究材料、旧报告和仓库均只读。不提交、不推送、不发布 release，不覆盖用户已有工作。
