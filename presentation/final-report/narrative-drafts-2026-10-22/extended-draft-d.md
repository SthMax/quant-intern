# 第 4 页｜LLM 可以怎样参与资料处理

LLM，也就是大语言模型，能够根据我们提供的问题和资料，参与阅读、归纳、分析和文字形成。

```text
资料与任务要求
    ↓
寻找相关信息 → 组织关系与解释 → 形成文字或结构化结果
    ↓
同事核对依据，决定怎样使用
```

它可以先从一份公告中整理日期、主体和金额，也可以比较几份材料中的不同说法。资料、问题和交付要求越明确，越容易检查它到底完成了什么。

这让许多原本需要反复阅读和整理的工作，有了新的辅助方式。

---

# 第 5 页｜前台、中台、后台有哪些具体用法

**投研：把分散信息组织成研究线索。** 易方达参与的 MENTOR 研究，使用中文文章和英文财经新闻，逐步识别热点事件、推演后续事件，再形成行业排序。这是一项公开研究原型，让我们看到文本怎样进入投研过程；论文实验尚不能说明公司实盘采用情况。

**合规：让内容作者先看到需要修改的地方。** 盈米的内容合规审查 Skill 接收文本或文档，返回风险位置、理由和修改建议。内容作者可据此修改，再提交终审。它把初稿自查接到既有审核流程中。

**技术支持：把模型接入开发与测试。** 易方达在协会发布的云平台案例中，披露将大模型用于开发、测试环节。研发人员可以在代码与测试工作中使用辅助能力，产物继续进入原有交付流程。整个平台的效率变化不能全部归因于大模型。

这些案例的共同点，是让模型参与一段具体工作，并把结果交回能够检查和使用它的人。

# 第 6 页｜应用走进公司后，需要安排什么

公开新闻、财报与内部研究文件，对使用环境的要求并不相同。一个工具开始帮助同事完成工作，也就开始接触不同范围的资料。

| 使用中会遇到的问题 | 需要明确的安排 |
| --- | --- |
| 谁可以使用这项能力？ | 身份、用户范围与使用入口 |
| 本次任务可以读什么？ | 文件权限、资料来源与可访问范围 |
| 结果怎样进入后续工作？ | 引用、复核和交付流程 |
| 模型在哪里运行？ | 运行位置、服务连接与维护责任 |

这些安排让工具能够进入日常工作。安全与合规也落实在这些具体条件之中。

# 第 7 页｜本地部署让公司能够管理运行环境

公司的需求，是在自己掌握的环境中使用 LLM 的能力。

本地部署把模型放到公司管理的设备上，便于安排运行位置、服务连接和资源使用。资料访问还要由身份、权限与应用流程共同控制：模型装在本地，并不会自动知道某位同事能看哪些文件。

因此，这次研究的重点是建立一套有依据的选择：**用什么模型，怎样把它运行起来，以及为此准备多少资源。**

要理解这些选择，可以先看看模型怎样完成一项大家熟悉的任务。

# 第 8 页｜第二章：一项分析任务对模型提出什么要求

把一份财报交给本地模型，看看从提供材料到得到解释之间发生什么。

---

# 第 9 页｜请模型解释收入和利润为什么变化

> 请阅读这份公司的财报，解释本期收入和利润变化的主要原因，并指出各项判断的依据。

一份有用的回答，需要把几件事连起来：先读对数字和单位，再区分本期、上期以及可比口径，最后让原因解释得到财报正文或附注的支持。

| 要交付的内容 | 同事怎样核对 |
| --- | --- |
| 主要收入、利润及变化 | 回到对应报表，检查数字、期间和单位 |
| 变化原因及相关业务 | 查看管理层解释、分部信息和必要附注 |
| 依据与仍不确定之处 | 打开引用位置，判断材料是否支持结论 |

这是用来理解技术的任务示意，尚未展示一次已经完成的财报分析实验。

---

# 第 10 页｜本地部署通常从已经训练好的模型开始

模型在训练中形成处理语言和完成任务的能力，这些能力保存在大量数值参数中。部署时，我们通常取得已经训练好的模型，把参数加载到自己的设备上运行。

**参数提供已有能力，眼前的材料提供本次任务的信息。**

模型已有的语言和分析能力，并不意味着它已经读过我们手里的这一份财报。我们仍需要把财报和问题交给它，它才能围绕这些材料作答。

参数规模也不能直接替代能力评价。不同模型的结构、训练和任务表现都可能不同，后面需要用实际证据比较。

---

# 第 11 页｜眼前的财报和问题怎样进入这次回答

本次提供的材料、问题，以及需要保留的对话历史，构成模型可使用的**上下文**。模型利用这些信息生成回答，这个运行过程叫作**推理**。

```text
系统要求 + 财报内容 + 用户问题 + 已有对话
                    ↓
            本次输入的上下文
                    ↓
              已训练好的模型
                    ↓
           思考、工具请求或回答
```

输入和输出通常按 **token** 计量。Token 是模型处理文本的片段，可能对应字、词或部分字符，不宜用一个固定比例换算成中文页数。

上下文窗口有上限。材料、历史和生成内容需要共同安排空间，不能把全部窗口都预先塞满材料。

---

# 第 12 页｜材料能放多少，与模型能用好多少，是两个问题

上下文决定一次任务能带入多少信息。窗口较长，就有机会同时放入更多报表、附注和相关材料，减少反复删减与重新提供资料。

能力决定模型怎样使用这些信息。它需要找到正确位置、联系不同段落，并分清哪些是事实、哪些只是可能的解释。

**材料放得进去，是完成任务的条件；回答是否准确完整，还要单独检查。**

“找到某个数字”“概括主要原因”和“列全所有明细”需要的能力并不完全相同。比较模型时，必须保留这种任务差别。

---

# 第 13 页｜完成这项工作，还要等多久

速度影响同事能否顺畅地把模型放进工作节奏。一次请求至少包含两段不同的等待。

```text
提交材料 ── 等待首次输出 ── 开始看到回答 ── 持续生成 ── 回答完成
```

**首次输出时间**告诉我们，交入材料后多久能看到模型开始返回内容。

**生成速度**通常用 token/s 表示，告诉我们开始输出后，内容以多快的速度继续出现。输出越长，总等待也越长。

如果模型先返回思考或工具请求，第一次有输出还不等于已经拿到最终分析。我们最终关心的是一项有用工作需要多久完成。

---

# 第 14 页｜固定硬件下，需要怎样的组合

| 维度 | 对工作的意义 | 比较时的问题 |
| --- | --- | --- |
| 上下文 | 同时带入多少材料与历史 | 所需信息能否放入，并留出生成空间？ |
| 能力 | 怎样理解材料、完成分析 | 结果能否达到这项工作的要求？ |
| 速度 | 等待多久、使用是否连贯 | 首次等待和后续生成能否接受？ |

固定设备的资源有限。更大的模型、更长的上下文或更多同时使用的人，会改变资源分配，也会改变体验。

这里有“不可能三角”的意味，但它描述的是当前模型和运行条件下的取舍。模型结构与推理优化也可能同时改善几个维度。

我们的目标，是找到适合当前工作的组合。先明确工作要求，比较才有方向。

先明确工作真正需要什么，再比较候选模型能提供什么。

# 第 16 页｜先把工作需要写成选型条件

本次研究区分个人工作与公司共享服务，两者使用同一组评价维度，但规模不同。

| 维度 | 个人工作／小组 | 公司共享长任务 |
| --- | --- | --- |
| 上下文 | 131K、262K 为基础档，继续研究 512K／1M | 为较长的多轮任务研究每会话 1M |
| 能力 | 文档提取、多文档分析、代码与文件辅助 | 在长材料上继续推理、调用工具并完成多步任务 |
| 速度 | 单人生成约 20 token/s 为体验目标 | 20 路活动请求，比较每路 10／20 token/s 目标 |
| 固定比较条件 | 单台 DGX Spark，128GB 统一内存 | 分别固定四卡或八卡服务器，再比较运行方式 |

这些是研究采用的规划条件，尚不是已经通过验收的服务承诺。

131K、262K、512K 分别指 131,072、262,144、524,288 总 tokens；1M 指 1,000,000。各档先留 8,192 tokens 给本轮生成，材料与历史使用剩余空间。

# 第 17 页｜候选模型怎样放在一起比较

个人路线主要比较 Qwen3.8-27B、Qwen3.6-35B-A3B 与相近规模的 Gemma；共享路线重点看 DeepSeek-V4.1-Flash、GLM-5.3-Flash，并保留 MiMo、Kimi 的任务能力参照。

比较不能只看模型名称旁边的一个分数。这里使用三类依据，分别回答三个问题。

| 依据 | 主要回答什么 | 阅读时保留什么条件 |
| --- | --- | --- |
| 作者公开评测 | 模型系统在哪些任务上表现较好？ | 题目、评分、工具、推理设置与版本 |
| 外部设备测量 | 某个组合实际有怎样的等待与速度？ | 硬件、模型、精度、输入输出与计时方式 |
| 资源计算 | 给定配置能容纳多少模型与会话？ | 内存布局、缓存格式、余量与并发假设 |

它们共同支持选择。公开能力分数不会直接变成本地速度，容量计算也不会直接变成业务成功率。

# 第 18 页｜上下文是否足以容纳我们的材料

Qwen3.8-27B 原生支持 **262,144 tokens**，模型卡提供扩展到 **1,000,000 tokens** 的配置。DeepSeek-V4.1-Flash 原生支持 **1M** 上下文。

窗口之外，还要看材料能否被有效利用。Qwen27 的公开结果说明，这件事与任务有关。

| 任务 | Qwen27 公开结果 | 结果说明什么 |
| --- | ---: | --- |
| AA-LCR v1.1：约 100K tokens 多文档问答 | 82% | 对跨文档寻找、组织答案提供能力依据 |
| ExtractBench：短文档完整字段提取 | 94.68 value F1 | 该提取流程在短材料上表现较好 |
| ExtractBench：超过 50 页的长文档提取 | 38.45 value F1 | 长列表、跨页字段的完整输出仍困难 |

F1 以 0–100 表示，综合反映提取值的准确与完整；它不是整份文档全部正确的比例。两种评测的任务与评分不同，不相加。

因此，长窗口值得保留；长文提取仍应分段整理、保存中间结果，并检查遗漏。

# 第 19 页｜模型能力的差别，会怎样影响工作结果

Finance Agent v2 让模型使用财报检索、网页读取和计算等工具，回答金融研究问题。它更接近“找到材料，再按财务口径分析”的工作过程。

| 作者榜模型标签 | 金融研究得分（%，越高越好） |
| --- | ---: |
| Qwen 3.8 27B | 48.55 |
| DeepSeek V4.1 Flash 原版 | 53.48 |
| DeepSeek V4.1 Flash 1017 | 56.96 |
| GLM 5.3 Flash | 57.85 |
| MiMo V2.6 Flash | 56.28 |

这是同一默认工具环境下、带关键条件门槛的加权部分得分，不能读成整题全对率；接近的分数也不足以说明显著优劣。

这组结果支持把 DeepSeek 纳入共享研究路线，同时把 GLM Flash 作为优先对照。Qwen27 则仍有个人文档工作的价值：ExtractBench 全集 value F1 为 **89.75**，高于该榜 DeepSeek 原版流程的 **87.11**。这比较的是各自完整提取流程，输入方式和推理设置并不完全相同。

选型应围绕任务展开，规模更大并不保证每类工作都更好。

# 第 20 页｜这样的模型在当前设备上用起来有多快

Qwen27 已有一条具体的个人设备性能依据：用户提供的单台 DGX Spark 外部测试汇总。

| 实际输入 tokens | 每次输出 tokens | 首次输出等待 | 后续生成速度 |
| ---: | ---: | ---: | ---: |
| 50,000 | 2,048 | 63.1 秒 | 21.01 token/s |
| 100,000 | 2,048 | 144.8 秒 | 20.11 token/s |
| 500,000 | 2,048 | 1,470.1 秒 | 14.82 token/s |

在 50K–100K 输入下，单人生成接近研究设定的 20 token/s 目标。到 500K，生成仍能继续，但首次等待已约 **24.5 分钟**，使用方式就需要重新安排。

测试使用随机 token，FP8 权重、FP8 KV 缓存及 MTP3 推测生成，关闭前缀缓存。这里先记住：这是一组具体运行设置的结果，其机制稍后展开。50K、100K 各两次，500K 一次；原始日志和业务质量评价尚未补齐。

共享模型目前没有同条件的本地速度横评，所以不把不同服务器或云端接口的速度排列成模型名次。

# 第 21 页｜当前模型选择，以及选择的边界

**个人工作与知识问答，以 Qwen3.8-27B 为起点。** 公开文档提取与多文档问答给出了能力依据，Spark 外测又提供了可理解的单人体验参照。长材料可以继续探索，但需要接受首次等待，并单独验收长文完整性。

**共享长任务，以 DeepSeek-V4.1-Flash 为主线。** 除金融研究表现外，它在 AA 的 AutomationBench-AA 为 69%、Terminal-Bench 4.0 为 27%，相应 Qwen27 为 48%、6%（作者分别采用 max 与 xhigh 标签）。这些分项支持继续研究较复杂的工具与代码任务，具体运行环境仍影响结果。

**保留 GLM-5.3-Flash 的同题对照。** 金融研究榜没有给出 DeepSeek 在所有任务上领先的结论。1017 已开放权重，可以作为升级候选；原版性能记录继续保留原版身份。

模型选择已经有了方向。接下来要解释，运行环境怎样把这些能力变成同事真正能够使用的服务。

# 第 22 页｜第四章：运行环境怎样影响使用体验

模型确定之后，一次请求怎样运行，决定同事实际会遇到怎样的等待。

---

# 第 23 页｜一次请求怎样经过本地推理服务

推理服务把模型持续加载在设备上，接收请求并返回结果。推理框架负责组织其中的计算、内存与调度。

```text
启动服务：加载模型参数 → 准备计算与缓存空间

同事提交请求
    ↓
检查请求与排队
    ↓
恢复可复用的历史状态（如果存在）
    ↓
处理输入 → 产生首个输出 → 持续生成 → 返回结果
```

一次请求通常不用重新加载整套模型，但仍要处理本次输入，并为会话保留必要状态。

输入处理和后续生成承担不同的工作。先区分这两段，才能知道等待在哪里，也才能判断优化是否解决了当前问题。

---

# 第 24 页｜设备内存里需要放下哪些东西

内存既要存放模型，也要容纳正在进行的工作。

| 占用 | 内容 | 主要随什么变化 |
| --- | --- | --- |
| 模型参数 | 已经训练好的权重 | 模型、存储精度与放置方式 |
| 会话状态 | 已处理历史的 KV 缓存，以及模型需要的其他状态 | 历史长度、会话数与模型结构 |
| 执行空间 | 临时计算、运行图、草稿网络等 | 框架、调度与优化配置 |

**KV 缓存保存注意力计算中可重复使用的历史表示。** 后续生成可以使用它，减少对旧输入的重复计算。Qwen27 还有递推状态，因此完整恢复不只涉及一种缓存。

FP8、BF16 表示不同的数值存储精度。较低精度通常减少占用，但具体节省与任务质量需要按模型和实现验证。

能放下模型，只完成了第一步。长会话与多人使用的空间，还要继续预留。

---

# 第 25 页｜回答出现之前，服务先处理输入

输入处理阶段称为 **prefill**。服务把已有的输入转成模型能够使用的表示，并建立后续生成需要的状态。

长材料需要更多计算。对于全注意力部分，新输入还要与前面的内容建立关系；模型采用稀疏或递推结构时，增长方式又会不同。

```text
首次输出等待
  = 请求进入与排队
  + 必要的状态恢复
  + 输入处理及首个输出
```

这解释了为什么“能装入 500K”与“交进去很快开始回答”是两件事。Spark 的 500K 外测首次等待约 24.5 分钟，其中包含完整读入长输入的过程。

如果旧前缀已经处理并保留，下一轮有机会只补算新增部分。这个机会要靠缓存与运行方式实现。

---

# 第 26 页｜回答开始之后，模型逐步生成内容

后续生成阶段称为 **decode**。新生成的内容成为下一步的条件，模型继续生成，直到本轮结束。

低并发时，设备可能需要为少量新输出反复读取权重和历史状态，所以内存带宽经常影响速度。更长的历史也可能增加每一步需要访问的内容。

**总完成时间既取决于每秒生成多少，也取决于最终要生成多少。**

举一个速度预算：若保持 20 token/s，生成 8,192 tokens 约需 **410 秒，即 6.8 分钟**。这还没有加入首次等待、工具执行和人工复核。

因此，输出应围绕需要的交付物组织。冗长的思考、日志与重复说明，也会占用窗口和时间。

---

# 第 27 页｜任务变长时，等待与资源怎样变化

同一台 Spark、同一组外测设置，把输入逐步加长后，两段体验的变化并不一样。

| 实际输入 tokens | 首次输出等待（分钟） | 生成速度（token/s） |
| ---: | ---: | ---: |
| 50,000 | 1.1 | 21.01 |
| 100,000 | 2.4 | 20.11 |
| 300,000 | 11.0 | 17.23 |
| 500,000 | 24.5 | 14.82 |

每次输出均为 2,048 tokens；前缀缓存关闭。300K、500K 各一次，较短两档各两次。

从 100K 到 500K，首次等待增长很明显，生成速度也逐步下降。长任务的主要改善方向因此很具体：减少重复读入，保留可复用状态，并把首次长输入安排到合适的时间。

另外一次 **999,936 输入＋64 输出**完成了 1M 总容量验证，首次等待约 **80.3 分钟**。它说明这组设置能够完成该容量请求；64 个输出还不足以代表长回答速度，更没有验证超长财报分析质量。

---

# 第 28 页｜多人使用时，服务还要安排请求

合批让不同请求共享一次权重读取，有机会提高总吞吐；每位同事自己的历史仍需要处理。新进入的长输入，也可能让正在生成的人等待。

Spark 外测中的三路请求，同时提交并各生成 4,096 tokens：

| 每路输入 | 三路共同生成时的总速度 | 共同窗口每路平均 | 各请求完整生成阶段的平均速度 |
| ---: | ---: | ---: | ---: |
| 50,000 tokens | 59.08 token/s | 19.69 token/s | 16.85 token/s |
| 100,000 tokens | 52.41 token/s | 17.47 token/s | 12.45 token/s |

“共同窗口”只取三路都已经开始、尚未结束输出的时段。完整阶段还受到其他请求处理输入的影响，更接近日常混合使用时会遇到的干扰。

调度可以把长输入拆成小块，在块之间继续服务正在生成的请求。块太小可能牺牲输入效率，块太大又会造成更长停顿，需要按真实负载调整。

同时登录的人、正在生成的请求、仍保留历史的会话，分别决定不同的资源需要。

---

# 第 29 页｜大模型怎样放到多张卡上运行

DeepSeek 原版的原生权重制品约 **510.286GB**。其中约 **202.758GB** 是 Engram 查找表及尺度，可以放在主机内存；剩余约 **307.528GB** 仍需按实际运行格式安排。

Engram 属于模型参数。它与随着对话增长的用户 KV 缓存，是两种不同对象。

```text
主机内存：Engram 参数表 ── 按需查找／预取 ──→ GPU 计算

GPU 组：模型的其余部分 + 各卡所需会话状态 + 执行空间
```

**张量并行（TP）**让多张卡分担一套模型的计算，同时引入卡间通信。八卡可以组成一个 TP8 服务，也可以分成两个 TP4 副本，各有自己的请求队列和缓存池。

分卡后，每类数据怎样分片、怎样复制仍取决于实现，不能把所有占用都直接除以卡数。以本研究的 H100／H200 缓存格式计算，20 份 1M 会话用于长历史的全局 KV，就需在**每张参与 TP 的 GPU 上占用 36.54GB**，还要再留其他状态和执行空间。

---

# 第 30 页｜不同框架怎样组织这些运行环节

框架选择首先要匹配模型与硬件，然后才比较体验与维护成本。

| 路线 | 与当前部署有关的能力 | 本次选择中的位置 |
| --- | --- | --- |
| vLLM | 分页管理、连续批处理、分块输入、前缀复用、多卡执行 | GPU 服务主线；已有 Spark 外测与 DeepSeek 公开回放可供核对 |
| SGLang | 前缀缓存、连续批处理、分块输入、多卡与分层缓存 | 保留为相同模型和负载下的重点对照 |
| modified vLLM／A100 | 为 A100 的 SM80 架构补齐算子、调度或通信适配 | 复用公司 A100 时采用的验证路线 |
| MLX、llama.cpp 等 | 对应个人平台、多种设备或不同模型格式 | 在硬件条件变化时重新比较 |

A100 的适配主要解决旧硬件怎样执行当前模型的问题。模型本身提供的稀疏结构、Engram 与长历史机制，不应全部算成适配项目的创新或收益。

新增部署可把 vLLM **0.32.0**作为固定版本候选；历史测量使用其原镜像继续解释。当前没有本项目同条件的全框架跑分，不能据功能表宣布速度冠军。

# 第 31 页｜缓存与推测生成，分别改善哪一段等待

**前缀复用减少重复输入计算。** 系统提示、旧材料和历史保持匹配，兼容的状态又仍然存在，下一轮才有机会跳过已做过的工作。把闲置状态转存到内存或 SSD 可以延长保留时间，但恢复也有成本。

Spark 的 CPU 与 GPU 共用物理内存，单纯把对象改放到 CPU 侧不会增加总容量；SSD 才提供另一层存储。保存聊天文字能重建内容，保存完整兼容状态才有机会省掉重算。

**MTP／推测生成尝试一次提出多个后续 token，再由目标模型验证。** 接受得多、额外开销合适，才可能加快生成。

| Spark 300K 输入诊断 | 生成速度 | 草稿接受率 |
| --- | ---: | ---: |
| 草稿长度仍停在 262,144，发生配置故障 | 5.80 token/s | 0.0% |
| 草稿上限同步到 1M 后重测 | 17.23 token/s | 99.4% |

这说明配置必须完整匹配；它不是正常关闭 MTP 与开启 MTP 的加速比较。随机负载的接受率，也不能直接套到财报或代码任务。

# 第 32 页｜已有共享服务回放告诉我们什么

DeepSeek 原版的公开 AgentX 多轮回放，提供了多卡共享运行的参照。

| 配置／活动会话数 | 平均输入 tokens | 前缀命中率 | 系统端到端输出（token/s） | p95 首次输出等待 |
| --- | ---: | ---: | ---: | ---: |
| 4×H200，TP4／16 | 138,189 | 95.1% | 614.76 | 3.03 秒 |
| 4×H200，TP4／32 | 149,855 | 95.2% | 922.61 | 5.12 秒 |
| 8×H200，TP8／32 | 156,951 | 95.7% | 1,052.18 | 2.63 秒 |

p95 表示约 95% 请求的等待不超过该值。活动会话可能处在不同阶段，不能把系统总输出直接除以人数，当作每人持续生成速度。

四卡从 16 个活动会话增加到 32 个，总输出提高，p95 等待也变长。八卡记录显示了另一种吞吐与等待组合，值得在相同工作负载下继续比较。

这些记录使用旧 vLLM 镜像、高缓存命中和**合成 DSpark 平均接受长度 3.51**，平均输入约 140K–160K。它们没有测出 20 路 1M 真实任务的服务水平。

# 第 33 页｜当前运行方案能提供怎样的服务

**个人路线已有具体的速度参照。** Qwen27＋Spark 的 50K–100K 单请求生成接近 20 token/s；超长输入需要安排首次读入，热续跑与业务质量继续验证。

**共享路线已有运行与容量研究基础。** DeepSeek＋多卡 vLLM 可以比较一套 TP8 与两套 TP4。两套独立服务默认各存一份 Engram；同一服务中的两组四卡副本，即 TP4×DP2，在满足同机共享条件时可以共用主机中的 Engram 表，但 GPU 模型副本和会话缓存池仍各自存在。

下一步的服务目标应写得具体：20 路每人 20 token/s，需要系统持续输出 **400 token/s**。20 路各采用 1M 总上下文时，能否达到这一速度，还要连同首次输入、热恢复和真实任务质量一起验收。

到这里，硬件一直是比较的给定条件。接下来把它变成可以调整的选择，看增加投入会改善什么。

# 第 34 页｜第五章：为需要的性能准备多少资源

# 第 35 页｜增加资源，能改变哪些限制

更大内存首先增加可保留的模型与历史；更多计算、带宽和合适的互联，才有机会改善等待和吞吐。

根据 DeepSeek 的公开启动记录，把运行图等额外占用也扣除后，再留 10% token 余量，得到下面的容量估算：

| 固定部署 | 20 份独立会话平均可分配的总 context | 20×1M 容量 |
| --- | ---: | --- |
| 8×H100，TP8 | 242,240 tokens／份 | 不足 |
| 4×H200，TP4 | 762,048 tokens／份 | 不足 |
| 8×H200，TP8 | 上限取 1,000,000 tokens／份 | 可作为候选 |
| 8×H200，两个 TP4，每组 10 份 | 上限取 1,000,000 tokens／份 | 可作为候选 |

这是基于旧镜像启动记录的线性预算敏感性，尚不是按新预算重新启动后的测量；也不承诺满窗口生成速度。

如果 20 项任务正在生成，另有 20 项等待工具却保留历史，就要安排 **40 份状态**。八 H200 TP8 此时约能分配每份 636K，说明任务暂时停下来，资源需要仍然存在。

# 第 36 页｜费用比较先约定同一套假设

成本比较需要把设备、实施、运维与日常工作量放进同一个范围。作为对照，API 路线通过网络按调用量购买供应商的模型服务。

本次三年预算采用以下条件：

- 个人中情景：首年每天 3 项任务，每年增长 10%；公司中情景：20 人首年各每天 5 项，每年增长 25%。每年按 250 个工作日计算。
- 每项任务先预算 8 轮模型调用：首轮输入 100K，每轮输出 2K，后续每轮新增 8K 资料；再增加 10% 完整轨迹，准备重试和修改。
- 一份 8 轮轨迹累计提交 **1.08M 输入**、生成 **16K 输出**，最后一轮总长 **172K**。多轮提交的旧历史按缓存规则分别计量。
- 本地与 API 都保留必要的应用、工具和技术人力；公司工具 CPU 的 18 万元只计一次。

本地可复用前缀按 90%、API 按 95% 命中规划，均非本次实测。硬件使用 10 月 12 日情景预算，API 使用 10 月 20 日公开价；汇率按 7.00、技术人力按 2,500 元／人天估算。三年保持相同费率。

不同路线尚未完成同一业务验收。因此，这里比较的是相同计划交付量下的条件预算，质量、重试与人工复核仍需用实际记录替换。

# 第 37 页｜不同配置与使用规模，对应多少投入

| 中等工作量情景 | 本地配置 | 三年计划任务量 | 本地三年总投入 | DeepSeek API 三年对照 |
| --- | --- | ---: | ---: | ---: |
| 个人 | 1 台 Spark＋Qwen27 | 约 2,483 项 | **9.05 万元** | **1.66 万元** |
| 公司共享 | 8×H200＋DeepSeek，另含工具 CPU | 约 95,313 项 | **392.54 万元** | **68.34 万元** |

总投入包含硬件、实施与持续运维等项目。公司本地方案中，GPU 整机约 **297.36 万元**，占总额约 **75.8%**；三年运维技术人力另为 **45 万元**。固定设备投入是主要差额。

API 对照只用于公开或已经获准使用的资料。它说明当前使用量下的经济差异，不能代替对资料范围与运行控制的判断。

公司预算假设系统能够提供 8,000 未缓存输入 tokens/s 和 400 输出 tokens/s，按每年 2,000 服务小时、70% 时间预算规划。这是待验收的服务能力，尚未证明上述交付量已经实现；日常 100K–170K 输入也不能替代 1M 满窗口测试。

# 第 38 页｜增加的投入换来了多少改善

**先看配置差额对应哪种能力。** 在同一套 10 月 12 日估算方法下，八 H100 整机约 **285–298 万元**，八 H200 约 **291–304 万元**。逐项同口径预算差约 **5.68 万元**。

结合前面的缓存计算，这一差额主要支持更大的会话容量：八 H100 的 20 份会话约为每份 242K，八 H200 则可把 20×1M 列为容量候选。它为优先研究 H200 提供了理由，但交付与支持仍需取得实际报价。

**再看任务增长是否需要继续买机器。** 公司较高工作量情景，三年任务数为 50,000、75,000、112,500。按当前服务预算，一台每年约能承担 64,487 项，因此第二年就需准备第二台。

| 公司情景 | GPU 节点数：第 1／2／3 年 | 三年本地总投入 |
| --- | --- | ---: |
| 中等工作量 | 1／1／1 | 392.54 万元 |
| 较高工作量 | 1／2／2 | 712.78 万元 |

任务增加可以分摊固定成本，也会用完机器能力。成本曲线因此出现扩容台阶，不能沿单机分摊一直下降。

# 第 39 页｜当前用途下，怎样的投入较为合适

**先让个人与小组形成真实使用记录。** Spark 硬件约 5.8–6.2 万元，完整三年个人中情景约 9.05 万元。它有较低的试用投入，可以先验证文档与代码任务的价值，再判断是否扩大规模。

**公司长任务保留八 H200 作为容量方案。** 20 路 1M 上下文的目标使它具有研究价值；是否采购，应由实际任务量、等待要求与报价共同决定。当前中等工作量下，单纯替代可外发任务的 API 消费，还不足以支持新购服务器回本。

**已有 A100 值得先验证复用。** 研究按 modified vLLM 路线估算，复用八 A100 的三年资源投入约 134.42 万元，低于新购 H200；但 A100 的长窗口容量和目标速度尚未验收，不能据此认定两者服务等价。

最终应计算每项按时、合格完成的任务花了多少，同时记录人工复核和净节省时间。释放的工时有使用价值，只有实际减少外包、加班或新增用工支出，才形成对应现金节省。

# 第 40 页｜第六章：把部署方案接回日常工作

模型与运行环境准备好之后，同事从哪里使用，又怎样接入工作需要的资料？

# 第 41 页｜同事怎样使用这项本地服务

使用入口可以随工作方式不同而不同，底层模型服务则可以共用。

```text
个人文件与代码工作
员工电脑上的 OpenCode／文件工具 → 本地模型服务 → 修改与结果回到工作目录

公司共享任务
浏览器入口 → 身份与任务管理 → Hermes 等任务执行层
                                   ├→ 模型服务
                                   └→ 隔离的文件、代码与工具环境
```

任务执行层负责在模型与工具之间组织多轮工作：模型提出操作，工具返回结果，模型再继续处理。

这些是研究中的接入方案，尚未表示公司服务已经上线。远程执行时，工具读取的是执行服务器获得授权的文件，不会因为同事打开了浏览器，就自动读取其个人电脑目录。

---

# 第 42 页｜工作需要的资料和工具怎样接进来

公司知识库可以先找到与问题有关、且当前用户有权读取的内容，再交给模型回答。这种做法称为检索增强生成，通常简称 **RAG**。

```text
用户身份与问题
    ↓
在获准范围内检索资料 → 授权过滤 → 重排相关片段
    ↓
模型根据片段回答 → 同事打开引用，重新核验访问权限
```

研究保留两条平台路线：Onyx Enterprise，以及 Milvus＋自建 RAG 服务＋Open WebUI。前者集中提供企业知识平台能力，后者由团队组合并维护检索、权限和应用；具体 NAS 连接与撤权都需要验收。

工具接入还可以提供文件读取、计算和代码执行。Skills 保存可复用的操作说明，MCP 等接口连接外部工具；身份、允许执行的动作和结果记录仍由整体系统安排。

# 第 43 页｜把尚未确定的问题放到真实使用中验证

先从有明确产物的工作开始，才能知道工具有没有帮到同事。

| 先验证什么 | 交付与检查方式 | 结果影响什么选择 |
| --- | --- | --- |
| 公告字段提取 | 字段表与出处；核对主体、日期、金额、遗漏 | Qwen27 是否足以承担第一批文档工作 |
| 研究代码辅助 | 可复跑的修改、测试与结果文件 | 工具执行与模型配合是否可靠 |
| 财报比较 | 数字、期间、口径、计算文件与引用 | 共享模型是否带来足够的质量收益 |
| 权限知识问答 | 有权可见、无权不可见；撤权后重新测试 | 资料接入能否扩大到公司环境 |

同时记录首次等待、生成停顿、完整任务时间、重试和人工复核。长任务再单独测 512K／1M、真实推测接受率，以及多人使用时插入长输入的干扰。

这些记录会把目前的能力证据、资源估算和成本预算，逐步换成公司自己的使用依据。

# 第 44 页｜回到公司的本地部署需求

这次研究已经把本地部署拆成了能够比较和解释的选择。
