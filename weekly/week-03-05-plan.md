## 3. 两种部署场景与选型原则

### 3.1 先固定负载口径

| 项目 | Personal LLM | 小型数据中心集中服务 |
|---|---|---|
| 用户与资源 | 一名使用者的一台受管理专业工作站 | 数十名使用者共享一套内部服务 |
| 主要任务 | 公告提取、资料阅读、个人问答与代码辅助 | 同类任务，加上多用户权限、并发、集中资料更新与运行管理 |
| 容量验证 | 先测单请求体验和小批量处理 | 同时观察活跃会话、到达请求、正在推理请求与排队情况 |
| 物理方案起点 | 按27B/35B及相近规模Gemma需求评估大显存GPU、单机多卡或较大统一内存 | 按模型质量、并发和可用性评估单机多卡、模型副本及必要的多节点；大型模型不预先限定必须单节点装载 |
| 维护重点 | 安装升级、资源占用、数据保存位置、恢复方法 | 身份接入、权限、限流、监控、版本回滚、备份与运行责任 |
| 成本口径 | 单台成本；若推广到多人，需要按设备数和维护工作量累计 | 共享利用率、峰值余量、基础设施与运维成本 |

“几十人同时使用”暂保留两种含义供确认：几十个活跃用户，以及几十个请求在同一时刻持续生成。容量分析覆盖后一种更重负载，不能把几十个账号自动解释为少量并发。

第3周填写以下参数：目标人数与峰值、每人每小时请求数、输入/输出token长度分布、对话与批任务比例、可接受等待时间、服务时段、停机容忍度、资料规模与更新频率。**规划测试档位**为1、4、8、16、32、50个客户端并发；它们是敏感性测试点，不是已经确认的业务需求或硬件能力。

短问答、长材料摘要和批量事件提取分开报告。模型的一次任务若会触发多次调用，计算容量时计入这些调用和重试。硬件不足时报告实际测试上限，较大场景使用有标注的估计和待验证项。

### 3.2 成熟稳定的判断标准

模型与软件分别筛选，最终评价的是**模型、推理引擎、硬件和任务的组合**：

- 官方权重或可信可追溯制品、清楚的使用许可，能够确定具体版本。
- 正式发布版本或可追溯的发布方构建支持所选模型、量化格式和实际硬件；固定版本/镜像，有可重复安装、验证和回滚步骤。
- 所需结构化输出、上下文长度、流式输出或工具格式能够在该组合上工作。
- 有维护记录、故障排查文档、升级和回滚方式；社区规模只作辅助证据。
- 标准部署路径能完成任务。需要长期维护私有补丁、实验分支或自写底层算子才能运行的组合不作为首选。
- 在相同质量和服务目标下比较显存、速度、人工修订与维护成本。新模型、最大参数量或最低量化位数都不自动获得优先级。

模型能力与部署准备程度分别记录。维护中的主流引擎对新模型的支持持续核验；某个旧tag缺少注册项只说明该组合尚未具备条件，不自动淘汰模型。研究时间优先用于标准配置、主流框架和可重复的发布方路径，避免长期维护私有改动。

当前核心10项为Qwen3.8-27B、Qwen3.6-35B-A3B、Gemma 4 31B/26B A4B、DeepSeek-V4.1-Flash、GLM-5.3/Flash、Kimi K3及9月22日按用户要求新增的MiMo-V2.6 Pro/Flash。原计划5–8项为初始比较规模，本轮扩展调查池；一个本地GPU原型的交付目标保持。Muse Spark 1.2及用户提出的潜在Qwen4、GLM5.4、DeepSeek V4.1 Pro、Kimi K3.1放在[候选池观察节](../knowledge-base/models/model-survey-2026-09-16.md)，未发布项目本轮不深入研究。

许可按[专项研究](../knowledge-base/models/license-review-2026-09-16.md)逐项核对，覆盖商业用途、集团关联方、内部使用与输出、修改分发、MaaS附加条件。美国厂商模型作为可能的总部偏好情景保留，当前没有已确认的机构国别准入要求。

选择当前可用且维护中的稳定版本。旧模型只有在支持、质量或资源方面仍有明确优势时才作为比较基线。先用提示词、结构化输出和任务所需检索完成基线；微调需求写入比较表，只有可重复的错误分析能说明其必要性时再评估。

### 3.3 软件与架构的初始方向

以下是基于官方文档的**候选路线**，不代表已经验证的性能、COD兼容性或最终采购建议。文档核查日期为2026年9月15日，实施时固定版本。

| 层次 | 初始方向 | 本阶段需要验证的内容 |
|---|---|---|
| 个人推理 | 依据专业工作站平台评估llama.cpp/Ollama或GPU服务引擎 | 所选模型、精度、上下文和实际GPU支持，结合运行维护选择。已有[Ollama](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)及[llama.cpp](https://github.com/ggml-org/llama.cpp#description)参考，具体组合待核 |
| 共享推理 | 对照vLLM与SGLang的官方模型部署路径 | 请求调度、显存、结构化输出和负载延迟；固定发布构建并实测。Qwen3.6的[模型卡](../knowledge-base/sources/TECH-013/original.md)分别给出引擎版本建议，GLM与Kimi卡片也列两类路径 |
| 检索与存储 | 优先复用已有存储；若已有PostgreSQL，可评估pgvector | 数据量、检索效果、文档权限与备份是否满足任务。[pgvector](https://github.com/pgvector/pgvector)提供PostgreSQL向量检索；是否采用取决于现有IT环境 |
| 应用与编排 | 固定任务流程、清楚的HTTP/JSON接口，工具访问独立封装 | 可重复运行、错误处理、超时与重试上限；如需框架，选一种有明确收益的维护中框架 |
| 部署与运行管理 | 单机优先使用标准服务或容器及既有监控 | 安装、重启、健康检查、日志、版本回滚；已有统一平台时接入现有平台 |

集中服务的逻辑顺序为：用户入口 → 身份与请求管理 → 任务服务 → 按需检索或受控工具 → 模型推理 → 输出校验及业务复核。权限应在检索和工具执行前实施。记录各环节的耗时，使慢检索、慢模型和排队能够分别定位。

个人方案保留同样的任务输入输出，但可将服务合并在一台机器上；集中方案再增加共享资料、用户隔离和运行管理。OCR、嵌入、重排、日志和工具的数据处理位置一并画入架构。

资源选择区分“模型装不下”和“吞吐不够”：前者评估受支持的更小模型、精度或单机多卡，后者在测量后评估模型副本和请求调度。[vLLM并行部署文档](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/)也按单卡、单节点和多节点的装载条件区分路径。多节点、复杂集群编排和研究型Agent框架只有在本阶段需求能说明必要性时才进入实施范围。

### 模型比较应填写的字段

5–8项以清楚的模型制品和版本计数，覆盖个人与集中服务的资源范围，并包含跨模型系列的比较。同一权重不同量化方式作为配置变体，不能重复计数。只做文献比较的模型与本地运行过的模型分别标注。

必填字段包括：官方来源与许可分类、中文及英文能力证据、总参数与激活参数、精度和量化来源、上下文限制、权重/缓存/运行内存需求、支持的引擎与硬件、结构化输出与工具能力、推理速度及其测量条件、微调需求、维护证据、已知限制和淘汰理由。

优先筛出满足任务质量与部署支持要求的组合，再比较延迟、资源和维护负担。大MoE模型需要按实际权重装载和缓存实现估算内存，不能用激活参数替代总权重大小。公开速度数据只在条件可比时引用，无法比较时保留空缺及原因。

## 5. PoC与可复用评价设计

### 主任务：公告事件提取

沿用当前报告的首个原型方向。使用公开且允许用于本实验的公告，抽取公司、事件类型、发生或披露时间、事件状态、数量、单位和原文证据位置。首次可得时间由数据记录提供，不让模型猜测。

流程保持明确：读取材料 → 调用本地模型 → 校验结构与字段 → 对照原文评分 → 保存结果。数值计算、代码匹配和去重由程序完成。先验证模型能否稳定产生可用信息，再决定是否扩展检索、工具调用或因子研究。

RAG作为汇报中的详细技术案例，与首个GPU任务有不同目的。若第4周基本原型完成，可用同一模型加一个小型检索问答流程；只有实际运行文档入库、检索和生成链路后，才报告端到端RAG结果。

### 三类评价任务

以下样本数是控制实习工作量的初始提案，按资料与标注条件调整，不代表生产验证规模。开发样本和保留测试样本按文档分开，调整提示词时不查看测试答案。

| 任务 | 开发集 / 保留测试集提案 | 指标与输出 |
|---|---|---|
| NER与事件提取 | 20 / 60个文档片段，分别记录实体与事件字段标签 | 实体级precision、recall、F1；事件状态、数值单位、证据句正确率；结构化格式成功率 |
| 金融问答 | 10 / 30个问题，包含资料不足、时点和数值问题 | 答案正确性、引用支持、恰当弃答；若使用检索，再单列检索召回和端到端质量 |
| 多文档摘要 | 5 / 10组材料，每组约3–5篇 | 要点覆盖、忠实性、冲突与时间处理、引用和人工修订时间 |

问答先使用给定证据评价模型阅读能力，再按需要增加检索评价，避免把检索失败全部计成模型推理问题。摘要使用统一评分说明与人工核查，记录实际复核者；无法取得业务人员评价时如实标注。三种任务共用配置、运行、结果和评分入口。

第3周末在评测文件中写下任务质量和服务目标，标明哪些经mentor确认、哪些为暂定。测试后按原口径报告，任何调整都记录原因。至少记录失败、超时和格式不合格样本，不只保留成功输出。

### 性能与运行稳定性

- 分别测冷启动与预热后表现。记录首次返回token的时间（TTFT）、完整响应时间、单请求生成速度、服务总吞吐，以及显存/内存峰值。
- 固定输入材料、输出长度上限、推理模式和生成参数，记录实际输入/输出token数。换模型时保持相同业务文本，说明tokenizer差异。
- 按第3节并发档位逐步增加负载，记录实际完成请求率、排队、错误与延迟p50/p95。计划对关键配置每轮至少100个请求、重复3轮；资源不足时报告实际样本量和分位数的局限。
- 增加带到达速率的请求回放，避免仅靠固定并发隐藏排队。区分批任务与交互请求，观察长任务是否影响其他用户。
- 选择代表性配置连续运行至少2小时，检查重启恢复、过长输入、请求取消、超时、过载处理及资源释放。此时长是PoC检查范围，不足以证明生产长期可用性。
- 分开记录模型服务与完整任务链路耗时。若有检索、OCR、嵌入或重排，也计入端到端资源和延迟。

复现记录包括GPU/驱动、CPU/RAM/OS、模型与tokenizer版本、引擎版本、精度、上下文、提示词、数据划分、运行命令、原始输出和评分。跨机器或跨后端结果分别呈现。CPU演示、API调用或模拟负载不能代替总计划要求的本地GPU部署结果。

## 6. 参考架构与经济性输出

### 第5周应完成的架构内容

在现有[参考架构](../knowledge-base/infrastructure/reference-architecture.md)中给出个人与集中服务两个分节，均包含：

1. 适用工作、质量与响应目标、使用人数及负载假设。
2. 逻辑组件和完整数据流，标清模型、检索、工具与人工处理的职责。
3. 物理配置表：GPU与显存、CPU、RAM、存储容量与备份、网络与互联需求。
4. 模型、推理引擎、资料存储、应用编排和监控的选择理由及版本。
5. 容量依据：权重、KV cache或对应架构缓存、运行开销、辅助模型与余量；并发、延迟和吞吐的实测范围。
6. 日常运维：用户与资料权限、更新、回滚、备份恢复、监控和责任人。
7. 单机故障影响、是否需要备用节点，以及增加该节点的成本和收益。

参考架构采用条件式配置：先写满足要求的资源范围和配置依据，取得可信测量或报价后再补具体规格。未取得COD输入时称为通用候选架构，并明确差异待核；不能称为已经适配实习机构生产环境。

### 本阶段就要考虑的经济性

在[现有TCO文件](../knowledge-base/infrastructure/tco-model.md)中补充Phase 2输入，不另建一份竞争性的成本模型：

- 个人方案的设备数量，以及多人推广时的集中管理和逐台维护成本。
- 集中方案的共享利用率、峰值余量、备用资源与可用性目标。
- 设备、存储、网络、设施、软件支持的配置依据或带日期报价。
- 测得的资源、token用量、重试、运行时段、维护工时和人工修订时间。
- 现有设备复用与新购分别估算增量支出和整体成本，不能把既有设备一律视为免费。
- 同一质量标准下的每项合格任务成本，以及低/中/高使用量下的成本变化。

第3–5周产出资源和成本驱动的初步范围，用于排除明显不合适的路线。完整的三年本地/API TCO、盈亏平衡、3–5项pilot候选及2–5项最终方案继续在第6–8周完成。外部API可作后续比较对象，其是否允许接入与其经济性分别判断。ROI使用本项目测得或明确假设的时间节省，不直接套用同业宣传数字。
