## Context与体验的统一研究口径

### 长度档位与实际占用

| 档位 | 跨配置计算采用的总tokens | 在本轮研究中的位置 |
|---|---:|---|
| 131K | 131,072 | 最低基础档，所有场景均纳入 |
| 262K | 262,144 | 第二基础档，用于观察长历史带来的资源变化 |
| 512K | 524,288 | 半百万级常用档候选；与此前写作524K的档位是同一个数值 |
| 1M | 1,000,000 | 长程Agent目标档；制品支持1,048,576时另外标明原生／配置上限 |

总context包含系统提示、工具定义、历史、当前输入、工具返回，以及模型生成的思考和答案。统一计算先预留8,192输出tokens，输入／历史预算为总context减输出预留。精确源样本仍保留其实际输入和输出；朋友的500,000＋2,048与999,936＋64不会改名为统一测试档。

**主比较按接近满窗口的实际历史计算。** 只把服务参数设到1M、实际输入仍很短的结果，登记为短负载；低于131K的测量用于机制分析和诊断。原RAG的8K结果保留原负载身份，场景2本轮增加的长会话基线用一行摘要呈现。

### 每个长度都研究四种请求状态

| 请求状态 | 固定条件／研究问题 | 需要报告的指标 |
|---|---|---|
| 首次完整读入 | 无前缀命中，读入接近窗口上限的材料 | 冷TTFT、prefill token/s、峰值内存；是否适合后台预加载 |
| 同一会话热续跑 | 精确前缀已驻留，新增1K／8K工具结果或指令 | 命中和新增tokens、热TTFT、状态恢复开销、每路decode |
| 缓存未命中或会话恢复 | 前缀改动、缓存被逐出、引擎重启或重新载入 | 重算／恢复时间、缓存工作集容量、主机RAM与存储开销 |
| 多人混合使用 | 一部分请求decode，一部分新增长prefill，其他会话等待工具 | 每路速度、尾延迟、排队、抢占、KV驻留和工具环境资源 |

前缀缓存的研究重点是后续轮次的输入处理；长历史在decode阶段的读取、计算和通信仍按对应长度计量。缓存命中率、前缀稳定性与可保留的会话数都进入模型，不将“每轮全部重算”和“每轮完美命中”混成一个平均体验。

### 体验目标与可用context

- **已确认的个人目标：单人decode 20+ token/s。** 10／15token/s可列作折中档，是否接受单独讨论；512K作为候选上限仍需对照20+目标。
- **热续跑等待：**先用“新增1K后，TTFT p95不超过5秒／10秒”两档工作假设筛选，待汇报讨论；新增8K另列响应曲线。样本不足时保留估计或待核状态，不从单次数据生成实测p95。
- **公司共享服务：**继续保留每人10／20token/s的目标敏感性，两档都给出可用context与并发。最终服务目标尚待确认。
- **首次加载和恢复：**分别给出实际分钟数、前台等待或后台准备方式及占用资源；单次冷启动可以接受多长时间另行讨论。
- **任务质量：**记录长距离信息引用、工具参数和状态连续性；有损摘要、历史截断和KV量化列明配置及质量证据。

每个配置都要回答两个方向：**给定并发，最大可用context是多少；给定每人512K／1M，最多支持多少同时活跃用户。** 内存、模型和Harness窗口、请求调度、每路速度、首token等待和任务质量共同决定结果；证据不足的组合保留为待验证候选。

交付表至少包含：硬件与拓扑、模型／精度、每人context、驻留会话数、活动请求数、冷／热TTFT、每路decode、系统吞吐、峰值缓存、证据类型及人民币成本。容量允许与体验达标分别给出判断。

## 工作线一 部署方案深化

### 场景1 从硬件比较转为具体使用方案

主问题是：一台Spark在单人20+目标下能稳定使用多大的context；512K日常档与1M长任务档分别需要怎样的缓存和调度安排。

1. **固定软件链路。** 围绕Qwen27、vLLM及一个Coding Agent入口整理标准路径；复用已有OpenCode／pi研究，选一条主讲组合。画清员工电脑、Spark模型服务、Skills／MCP、文件与产物的位置。
2. **描述代表任务。** 以代码／数据处理、财报与Excel比较、材料整理为例，展示输入、Agent步骤、工具执行与最终产物；单人使用为主，三人共用列为扩展。
3. **围绕长context整理证据。** 对131K／262K／512K／1M分别研究冷读入与热续跑。朋友的500K输入记录为14.82token/s、冷TTFT约24.5分钟，1M容量样本冷TTFT约80.3分钟；作为512K／1M研究的锚点，50K／100K结果用于解释趋势。单人131K／262K、长输出1M及热续跑数据缺口单列。
4. **明确单人和三人使用的资源竞争。** 对比一人独占、三会话驻留但只有一人生成、三人同时生成；每种状态都按每人实际长历史计缓存。4／8路CLI作吞吐诊断参考，不替代三人长context体验。
5. **核对整条链路的有效窗口。** 对齐模型／tokenizer／RoPE、MTP草稿、服务端max_model_len、Harness声明窗口、输出预留和压缩阈值。检查是否在达到512K／1M前就触发历史压缩，以及压缩后保留了什么任务信息。
6. **提出可讨论的运行档位。** 给出默认交互窗口、长任务窗口及三人共享窗口的候选值和进入条件。针对瓶颈分别研究前缀复用、缓存保留／恢复、chunked prefill、MTP和请求准入；同样写明其内存、质量与维护代价。
7. **补齐费用与维护。** 复核人民币整机价格，列出存储、客户端、软件部署、维护与模型更新工作量；价格、估算和现有设备复用分别标明。

**交付：**更新场景1正文，给出部署图、四档context与单人／共享体验矩阵、默认／长任务窗口方案和费用表。重点回答512K是否适合作为日常上限，以及1M更适合哪种使用方式。此前四硬件比较保留为历史选型依据。

### 场景3 按DeepSeek重新计算服务器方案

主问题是：以每人1M为长程Agent目标，在目标并发和响应条件下，A100／H100／H200各自能提供多大的有效窗口，哪套完整部署成本最低。

**模型和引擎先定清楚。** 固定DeepSeek-V4.1-Flash的官方版本、权重与量化制品，核对模型结构、主机内存使用、缓存表示及MTP资源。主讲部署对照vLLM／SGLang的可维护路径；A100定制runtime作为独立工程案例。按DeepSeek结构重算容量与性能，原MiMo测算保留为历史参考。

| 比较项目 | 本周处理方式 |
|---|---|
| GPU准确型号 | H200／H100区分NVL、PCIe、SXM等具体形态；A100区分40GB／80GB及PCIe／SXM，主比较先看80GB |
| 整机而非单卡 | 同时计CPU、RAM、SSD、互联、网卡、供电散热、支持及部署；先筛4卡／8卡，其他卡数由容量或项目证据说明 |
| 单请求如何用卡 | 比较TP、EP和服务副本的组合；注明NVLink／NVSwitch／PCIe拓扑、通信与主机内存路径 |
| 并发口径 | 先有单人长context参照，再比较5／20／30／50活动请求，**20为主表**；另外计入等待工具但仍占缓存的驻留会话 |
| 上下文 | **131K／262K为基线，512K为中间档，1M为目标档。** 核心对照为每人1M与20路活动请求，并反向求各整机在20路下的最大可用窗口 |
| 性能 | 每路decode、系统decode、端到端吞吐、冷／热TTFT及尾延迟、排队与缓存容量同时呈现；增加长prefill对其他用户decode的干扰情景 |
| 共享响应目标 | 列出每路10／20token/s两档筛选情景，作为待讨论服务目标；原“单人20+”继续专指场景1 |
| 经济性 | 在同一服务目标下比较整机投入、满足目标的并发槽位成本和运行费用；既有设备复用与新增采购分开 |
| 采购条件 | 沿用中国境内部署要求，更新准确SKU、可交付渠道、出口／再出口依据和报价日期 |

保留现有Hermes＋Skills／MCP主结构，细化一个代码或财报／Excel多轮任务：历史从131K增长到262K、512K、1M，每轮记录新增材料、工具结果、输出和前缀命中。检查任务等工具时的缓存驻留，以及会话被逐出后的恢复。模型节点和CPU工具执行池分别计容量及成本。

研究分两步：先筛权重、每卡缓存、运行缓冲、草稿及主机内存容量，再对容量可行的组合估算或核查冷／热响应与混合负载。优先完成20路主情景，再补5／30／50路的扩展边界。硬件不足以同时满足1M和目标并发时，表内呈现增加副本／卡数、减少活动并发或采用512K服务档的成本与体验变化。

**交付：**A100／H100／H200整机比较表、context×并发×体验矩阵、各配置的每人最大可用窗口与1M并发上限，以及完整人民币成本。费用比较固定相同context和服务目标。

## 工作线二 A100项目专项阅读

初步定位：[shi3z/deepseekv4.1-A100-custom](https://github.com/shi3z/deepseekv4.1-A100-custom)。README明确对应DeepSeek-V4.1-Flash与A100定制runtime；与用户线索高度吻合，项目身份可在后续补充线索时确认。

按以下顺序阅读和整理：

1. **README与启动脚本：**核对每个profile的GPU数量、显存、互联、权重身份、上下文、并发、缓存和MTP条件。启动示例中有Abliterated权重路径，需查明各组结果实际使用的制品。
2. **模型与内核实现：**追踪权重驻留、主机内存中的Engram、专家分片、批处理、前缀恢复及草稿验证，解释主要耗时怎样减少。
3. **benchmark脚本与原始结果：**逐项区分prefill／replay、单流生成、共同decode、端到端吞吐和峰值；另列Jev结构化候选评分的“有效吞吐”。把配置上限、实际输入、实际输出和缓存命中分别登记，高并发时同步缩短context的记录单独比较。
4. **正确性及运行证据：**检查输出对照、测试覆盖、错误与长context记录，并核对主流框架能直接采用的部分和需要维护的定制实现。
5. **回到本项目：**先核对131K／262K基础档，再评估512K／1M及20活动任务的资源和服务表现。优先寻找长输入prefill、满历史decode、前缀续跑与多会话驻留的依据，形成可借鉴机制、证据覆盖范围、额外资源和维护成本的说明。

**交付：**一份来源可追溯的专项笔记，主稿约2页：项目怎样运行，以及高吞吐的条件和对场景3的启示。已完成固定版本代码／profile／benchmark调用链检查、30组缓存复算及公开性能口径审查，见下方完成记录。
